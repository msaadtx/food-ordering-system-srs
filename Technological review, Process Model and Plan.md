**1.6 Technological review:**
Our Online Food Ordering System will use modern web and mobile technologies to give students a fast and easy way to order food at QAU. apps like Foodpanda already exist but they dont have features specific to university campus. Our system will have easy interface, database to store orders and user info, online payment and live order tracking to make food ordering better inside university.

We choosed these technologies because they are easy to use, have good documentation, mostly free or low cost and also good for a student level project like ours.

**1.7 Process model:**
For development of this system we are following the Agile Process Model. We choosed this model because our requirements can change as we learn more about student and hut staff needs, and agile let us build and deliver the system in small working parts (sprints) instead of waiting until the end to see results.

In this model the project is divided into short sprints, each around one to two weeks long. In every sprint we plan, design, build and test a small working part of the system. At the end of each sprint we review the work with our team and supervisor, take feedback, and use it to adjust the plan for the next sprint.

Main sprints of this project are given below:
* Sprint 0 — Project Initiation and Requirement Gathering: we find out all the funcitonal and non-functional requirements of the system and prepare the initial product backlog.
* Sprint 1 — System Design: we make all diagrams like use case diagram, class diagrams, sequence diagrams and overall architecture design.
* Sprint 2 to Sprint 4 — Module Development: we build each part of system one by one, in incremental sprints, like user registration, menu management and order processing etc, and demo each working increment at the end of its sprint.
* Sprint 5 — Testing: we test each module separately first (unit testing) and then test the whole system together (acceptance testing), on top of the testing already done within each earlier sprint.
* Sprint 6 — Review and documentation: we write the complete SRS document, do a final sprint review with retrospective, and finish all project work.

This approach helps us to find and fix mistakes early, adapt to changes in requirements, manage our work in a better way through regular sprint reviews, and finish a well-tested system before the deadline.
